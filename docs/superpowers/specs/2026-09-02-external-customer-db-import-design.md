# 외부 고객 DB 가져오기 설계

## 목적

기존 멤버십·포인트 시스템에서 사용하던 Excel/CSV 고객 DB를 LOOP 관리자 화면에서 불러와 현재 LOOP Google Sheet 구조에 맞게 안전하게 변환·이전한다.

핵심 목표는 다음과 같다.

- 사용자가 원본 엑셀을 별도로 가공하지 않아도 된다.
- 한 파일에 여러 시트가 있어도 모두 분석할 수 있다.
- 업체마다 다른 컬럼명을 자동 추정하고 관리자가 최종 확인한다.
- 방문포인트·도장·결제포인트를 서로 섞지 않는다.
- 기존 LOOP 고객과 중복될 경우 자동 합산하지 않는다.
- 실제 과거 날짜가 없는 데이터를 임의로 생성하지 않는다.
- 현재 고정한 Google Sheet 탭 구조를 바꾸거나 추가 탭을 만들지 않는다.
- 최종 반영 전 관리자에게 전체 변경 내용을 명확하게 보여준다.

## 고정 Google Sheet 구조

외부 DB 가져오기 기능은 아래 구조를 변경하지 않는다.

1. 대시보드
2. 고객_목록
3. 고객_방문기록
4. 고객_재방문설문
5. 포인트_전체거래내역
6. 포인트_방문적립내역
7. 포인트_도장적립내역
8. 포인트_결제적립내역
9. 설정_방문포인트혜택
10. 설정_결제포인트혜택
11. 설정_적립방식

외부 파일 원본이나 임시 Import 시트는 Google Sheet에 저장하지 않는다.

## 권장 아키텍처

### 1. 브라우저 파일 분석

관리자 브라우저에서 `.xlsx`, `.xls`, `.csv` 파일을 읽는다.

브라우저에서 처리할 정보:

- 파일명
- 워크시트 목록
- 각 시트의 행/열 수
- 헤더 후보
- 샘플 데이터
- 컬럼 자동 매핑 후보

원본 파일 자체는 서버나 Google Sheet에 업로드하지 않는다.

### 2. 정규화된 Import Payload

브라우저는 원본 파일을 LOOP가 이해하는 중립 구조로 변환한다.

예시:

```ts
{
  fileName: 'legacy-members.xlsx',
  sheets: [
    {
      name: '회원목록',
      role: 'customers',
      mappings: {
        phone: '휴대폰',
        visits: '총방문',
        visitPoints: '잔여P',
        lastVisit: '마지막방문'
      }
    }
  ],
  customers: [...],
  visits: [...],
  pointHistory: [...]
}
```

브라우저에서 값의 타입과 기본 형식을 정리하지만 최종 신뢰 검증은 서버에서 다시 수행한다.

### 3. 서버 검증 및 반영

새 관리자 전용 API에서 다음을 다시 검증한다.

- 관리자 PIN
- 전화번호 정규화
- 숫자 범위
- 날짜 형식
- 잔액 유형
- 시트 역할
- 중복 처리 정책
- 동일 파일/행 중복 입력 가능성
- 최종 확인 플래그

검증이 끝난 데이터만 기존 `lib/sheets.ts`의 고정 시트에 반영한다.

## 관리자 UI 흐름

관리자 대시보드에 `기존 고객 DB 가져오기` 섹션 또는 진입 버튼을 추가한다.

### Step 1. 파일 선택

지원 형식:

- `.xlsx`
- `.xls`
- `.csv`

업로드 직후에는 실제 DB를 수정하지 않는다.

화면에 표시:

- 파일명
- 파일 크기
- 발견된 시트 수
- 총 행 수

### Step 2. 전체 시트 분석

파일 안 모든 시트를 목록으로 표시한다.

각 시트는 아래 역할 중 하나로 지정할 수 있다.

- 고객정보
- 방문이력
- 포인트이력
- 제외

자동 추정 후 관리자가 변경할 수 있다.

예:

| 원본 시트 | 자동 추정 | 최종 역할 |
| --- | --- | --- |
| 회원목록 | 고객정보 | 고객정보 |
| 이용내역 | 방문이력 | 방문이력 |
| 적립내역 | 포인트이력 | 포인트이력 |
| 안내 | 제외 | 제외 |

### Step 3. 컬럼 자동 매핑

각 시트별로 컬럼을 LOOP 필드에 매핑한다.

고객정보 후보 필드:

- 전화번호
- 방문횟수
- 방문포인트
- 도장
- 결제포인트
- 최근방문일
- 최초유입경로

방문이력 후보 필드:

- 전화번호
- 방문일
- 결제금액
- 유입경로

포인트이력 후보 필드:

- 전화번호
- 날짜
- 적립/차감량
- 적립/차감 구분
- 잔액
- 내용
- 포인트 종류

자동 인식 키워드는 한국어와 흔한 영문 표현을 포함한다.

예:

- 전화번호: `전화번호`, `휴대폰`, `핸드폰`, `휴대전화`, `mobile`, `phone`, `tel`
- 방문횟수: `방문수`, `방문횟수`, `누적방문`, `visits`
- 포인트: `포인트`, `적립금`, `마일리지`, `point`, `points`, `balance`
- 최근방문일: `최근방문`, `마지막방문`, `last visit`

### Step 4. 포인트 종류 명시

`포인트`, `적립금`, `잔액`처럼 의미가 불명확한 컬럼은 관리자에게 반드시 LOOP 잔액 종류를 확인시킨다.

선택지:

- 방문포인트
- 도장
- 결제포인트
- 가져오지 않음

자동 추정은 제안일 뿐 최종 값은 관리자가 결정한다.

현재 매장의 활성 적립 방식과 다른 잔액으로 매핑하면 경고를 보여준다.

예:

> 현재 매장은 도장 쿠폰을 사용 중입니다. 업로드한 `포인트` 컬럼은 방문포인트로 보존됩니다. 잔액은 서로 자동 환산되지 않습니다.

## 데이터 정규화 규칙

### 전화번호

- 숫자 이외 문자를 제거한다.
- LOOP의 `normalizePhone()` 규칙과 동일하게 처리한다.
- 정상적인 국내 휴대전화번호 형태가 아니면 오류 행으로 분류한다.

### 방문횟수

- 0 이상의 정수만 허용한다.
- 빈 값은 `없음`으로 취급하며 임의로 0을 덮어쓰지 않는다.

### 잔액

- 방문포인트: 0 이상의 정수
- 도장: 0 이상의 정수
- 결제포인트: 0 이상의 정수

음수 잔액은 가져오지 않고 오류로 표시한다.

### 날짜

다음을 인식한다.

- Excel date serial
- `YYYY-MM-DD`
- `YYYY.MM.DD`
- `YYYY/MM/DD`
- 일반적인 한국식 날짜 표현

파싱할 수 없는 날짜는 해당 필드만 오류로 표시한다.

## 과거 방문 이력 처리

### 실제 방문 날짜가 있는 경우

실제 날짜 기준으로 `고객_방문기록`에 저장한다.

동일한 전화번호와 동일 날짜의 완전히 동일한 이력은 중복 후보로 분류한다.

### 실제 방문 날짜가 없는 경우

예:

- 총 방문 12회
- 최근 방문 2026-08-20

이 경우 `고객_목록.방문횟수 = 12`는 가져오지만 12개의 가짜 방문 행을 만들지 않는다.

`최근방문일`이 존재하면 고객 요약값에만 사용한다.

## 과거 포인트 처리

### 잔액만 존재하는 경우

예:

- 보유 방문포인트 8P

`고객_목록`에 8P를 반영하고 다음 기준 기록을 생성한다.

`포인트_전체거래내역`:

- 거래유형: `ADJUST`
- 변동포인트: `+8`
- 변동전잔액: `0`
- 변동후잔액: `8`
- 내용: `기존 시스템 DB 이전`

`포인트_방문적립내역`에도 동일한 의미의 초기 기준 원장을 기록한다.

도장과 결제포인트는 각자의 원장에 초기 이전 기록을 남긴다.

없는 과거 적립 날짜는 생성하지 않는다. 기준 기록의 날짜는 실제 Import 실행 일시로 한다.

### 실제 포인트 이력이 존재하는 경우

원본에 거래 날짜, 적립/차감량, 잔액 정보가 충분하면 실제 이력을 가져올 수 있다.

단, 원본 이력의 합계가 고객 요약 잔액과 맞지 않으면 관리자에게 불일치 경고를 표시한다.

관리자는 다음 중 선택한다.

- 이력 기준으로 계산
- 고객 요약 잔액 기준으로 마지막 조정 기록 추가
- 해당 고객 가져오기 제외

기본 추천은 `고객 요약 잔액 기준으로 마지막 조정 기록 추가`다. 원본 시스템의 현재 고객 보유 잔액을 보존하기 위해서다.

## 기존 LOOP 고객 중복 정책

중복 판별의 주 키는 정규화된 전화번호다.

중복 고객은 자동 합산하지 않는다.

비교 화면 예:

| 항목 | 현재 LOOP | 가져올 DB |
| --- | ---: | ---: |
| 방문횟수 | 3 | 12 |
| 방문포인트 | 5P | 8P |
| 도장 | 1 | 없음 |
| 결제포인트 | 0P | 없음 |
| 최근방문일 | 2026-08-01 | 2026-08-20 |

관리자 선택:

1. 기존 LOOP 유지
2. 가져온 DB 값으로 갱신
3. 항목별 직접 선택

`항목별 직접 선택`에서는 방문횟수, 각 잔액, 최근방문일, 유입경로를 개별 선택할 수 있다.

중복 고객에 대해 `현재 + 가져온 값` 자동 합산 옵션은 제공하지 않는다.

## 새 고객 처리

기존 LOOP에 없는 전화번호는 신규 Import 고객으로 생성한다.

- 고객 ID는 LOOP에서 새로 생성한다.
- 원본 시스템의 내부 회원번호를 LOOP 고객 ID로 사용하지 않는다.
- 개인정보 동의일시/버전은 비워둔다.
- 다음 실제 LOOP 방문에서 현재 개인정보 동의를 다시 받는다.
- 기존 포인트와 방문횟수는 동의 전에도 DB에 보존되지만 고객이 기능을 이용하려면 현재 동의를 완료해야 한다.

## 가져오기 미리보기

최종 적용 전 반드시 요약 화면을 제공한다.

예:

- 총 분석 행: 1,352
- 신규 고객: 1,102
- 중복 고객: 84
- 제외: 153
- 오류: 13
- 방문이력: 8,241건
- 방문포인트 이전: 18,420P
- 도장 이전: 324개
- 결제포인트 이전: 2,850,000P

오류 행은 행 번호, 원본 시트, 오류 이유를 보여준다.

관리자가 오류 행을 제외하고 정상 행만 가져올 수 있다.

## 최종 확인

최종 반영 버튼은 다음 조건을 모두 만족해야 활성화된다.

- 모든 사용 시트의 역할이 확정됨
- 필수 전화번호 매핑이 완료됨
- 애매한 포인트 컬럼의 잔액 종류가 확정됨
- 모든 중복 고객의 처리 방식이 선택됨
- 관리자 `위 내용을 확인했습니다` 체크

최종 요청에서 서버가 관리자 PIN을 다시 확인한다.

## Import API

새 API 경로 제안:

`POST /api/admin/import`

브라우저가 정규화한 payload와 관리자 선택 결과를 전송한다.

서버는 클라이언트의 총계나 검증 결과를 신뢰하지 않고 모든 값을 다시 계산한다.

응답 예:

```json
{
  "importedCustomers": 1102,
  "updatedCustomers": 84,
  "skippedRows": 153,
  "visitRows": 8241,
  "pointLedgerRows": 3120,
  "stampLedgerRows": 35,
  "paymentLedgerRows": 421,
  "storage": "google-sheets"
}
```

## 반영 순서와 실패 처리

Google Sheets는 다중 시트 변경을 하나의 DB 트랜잭션처럼 원자적으로 묶을 수 없으므로 Import는 단계별로 실행한다.

권장 순서:

1. 전체 payload 서버 검증
2. 현재 Customers 스냅샷 재조회
3. 중복 결정이 현재 상태와 여전히 일치하는지 검증
4. 원장/방문 데이터 쓰기 준비
5. 고객 목록 갱신
6. 필요한 원장과 방문 기록 추가
7. 최종 재조회 및 결과 검증

대규모 가져오기 중 일부 쓰기가 실패할 가능성을 줄이기 위해 여러 행을 한 번에 쓰는 batch update를 우선 사용한다.

Import 실행에는 클라이언트 생성 `importId`를 포함한다. 같은 Import 요청이 네트워크 재시도로 반복될 경우 동일 `importId`를 감지해 중복 기록을 방지할 수 있도록 설계한다.

현재 고정된 시트 구조에 Import 전용 시트를 만들 수 없으므로 idempotency는 서버 요청 단위와 각 원장 description/import metadata 전략으로 구현한다. 구현 단계에서 별도 저장소 없이 안전하게 보장하기 어려운 경우, 동일 payload 재전송 방지 수준으로 범위를 제한하고 UI에서 재실행 전 현재 상태 재검증을 강제한다.

## 파일 크기 및 사용 제한

초기 버전은 브라우저 안정성을 위해 다음 제한을 둔다.

- 파일 최대 10MB
- 최대 20개 시트
- 전체 데이터 행 최대 50,000행

제한 초과 시 파일을 분리해서 가져오도록 안내한다.

이 수치는 실제 테스트에서 조정 가능하다.

## 보안 및 개인정보

- Import UI는 관리자 인증 후에만 노출한다.
- Import API는 관리자 PIN을 반드시 다시 검증한다.
- 원본 엑셀 파일은 서버에 영구 저장하지 않는다.
- 원본 전화번호는 기존 고객 API처럼 일반 관리자 목록 응답에 노출하지 않는다.
- Import 미리보기는 업로드한 브라우저 세션 안에서만 원본 번호를 다룬다.
- 서버 로그에 원본 전화번호, 고객 행 전체, 엑셀 원본을 출력하지 않는다.
- Import 고객의 개인정보 동의 기록을 임의 생성하지 않는다.

## UI 원칙

- 기존 LOOP 관리자 디자인을 유지한다.
- 한 화면에 모든 옵션을 펼치지 않고 단계형 Wizard로 구성한다.
- 상단에 `1 파일 → 2 시트 → 3 컬럼 → 4 중복 → 5 검토` 진행 상태를 표시한다.
- 자동 추정은 파란/초록 계열의 `자동 인식` 배지로 보여준다.
- 사람이 확인해야 하는 항목은 경고 색상과 `확인 필요` 배지로 구분한다.
- 오류가 있어도 정상 데이터 미리보기는 가능하게 한다.
- 최종 실행 전에는 명확한 변경 요약을 가장 크게 보여준다.

## 필요한 코드 단위

### `lib/import-domain.ts`

- Import 타입
- 전화/숫자/날짜 정규화
- 시트 역할 추정
- 컬럼명 매핑 추정
- 행 변환
- 중복 비교 모델
- Import 요약 계산

순수 함수 위주로 만들어 테스트하기 쉽게 한다.

### `app/api/admin/import/route.ts`

- 관리자 PIN 검증
- 정규화 payload 재검증
- 현재 Customers와 중복 재검증
- 병합 정책 적용
- 고정 Google Sheet 구조에 batch write
- 결과 반환

### `lib/sheets.ts`

기존 고정 시트 구조는 변경하지 않는다.

필요한 batch 함수만 추가한다.

- bulk customer update
- bulk visit append
- bulk transaction append
- bulk point ledger append
- bulk stamp ledger append
- bulk payment ledger append

### `app/page.tsx`

관리자 대시보드에서 Import Wizard 진입 및 결과 반영.

규모가 커지면 `app/components/import-wizard.tsx`로 분리한다. `page.tsx`가 이미 크기 때문에 별도 컴포넌트 분리를 우선한다.

### 스타일

기존 관리자 스타일을 재사용하고 Import 전용 wizard, mapping table, conflict cards 스타일만 추가한다.

## 의존성

Excel 파일 파싱을 위해 브라우저에서 동작하는 `xlsx` 계열 라이브러리를 추가한다.

CSV는 같은 파서 또는 별도 경량 파싱으로 지원한다.

파일 파싱 라이브러리는 브라우저 번들에만 포함되며 서버에서 원본 파일을 해석하지 않는다.

## 완료 기준

다음 시나리오가 통과하면 기능 완료로 본다.

1. 외부 xlsx 한 파일에 3개 이상의 시트가 있어도 모두 목록에 표시된다.
2. 각 시트를 고객/방문/포인트/제외로 지정할 수 있다.
3. 흔한 컬럼명은 자동 매핑된다.
4. 포인트 잔액 종류를 직접 지정할 수 있다.
5. 기존 고객은 자동 합산되지 않는다.
6. 중복 고객마다 유지/갱신/항목별 선택이 가능하다.
7. 과거 방문 날짜가 없으면 가짜 방문 기록이 생성되지 않는다.
8. 현재 잔액만 있는 고객은 DB 이전 기준 원장을 가진다.
9. Import 고객의 기존 방문횟수와 잔액이 LOOP에서 그대로 조회된다.
10. Import 고객은 다음 실제 이용 시 현재 개인정보 동의를 다시 받는다.
11. 현재 Google Sheet 탭 구조와 순서가 유지된다.
12. Import 완료 후 관리자 고객 목록과 대시보드 수치가 새 데이터를 반영한다.
13. `npm test`와 `npm run build`가 성공한다.
14. Vercel Preview에서 Import UI와 API가 정상 동작한다.
15. `main` 병합 후 Production 배포 커밋 SHA와 READY 상태를 확인한다.
